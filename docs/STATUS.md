# 구현 현황 (Implementation Status)

`CLAUDE.md`에서 분리된 문서입니다. 기능이 실제로 백엔드에 구현되어 있는지 아닌지를 기능 단위로, 날짜와 함께 기록합니다. **새 기능을 완성했으면 이 문서를 갱신하세요** — CLAUDE.md에는 짧은 요약과 이 문서로의 링크만 남깁니다.

이 저장소는 **AX Document Platform**의 **backend**입니다 — 프로젝트 단위 문서를 공유 **Document Core**(File → Version → Section → Chunk → Embedding)로 통합 관리하고, 그 위에 proofread(오탈자 검증), 자동분류, 버전 diff, 규정검증, RAG 챗봇, 관련문서 추천 등 AI 기능을 얹는 프로젝트-스코프 문서 플랫폼입니다. 상위 모노레포 스타일 디렉터리(`sidepjt/`) 아래, 형제 폴더 `frontend/`(Next.js, 별도 git 저장소), `embedding/`, `storage/`, `models/`, `docker/`와 함께 있으며, 루트 `docker-compose.yml`이 부모 디렉터리에서 전체를 오케스트레이션합니다.

## What actually exists today (don't overstate)

- **DB / migrations**: the full Document Core schema (8 tables: projects, folders, documents, document_versions, document_sections, document_chunks, embedding_models, chunk_embeddings) + a `users` table, all created via **Alembic** migrations. `chunk_embeddings.embedding` is `pgvector.Vector(1024)`.
- **Auth**: Google OAuth + backend-issued JWT (access via `Authorization: Bearer`, refresh in httpOnly cookie), plus a `mock` provider for dev login without credentials. `get_current_user` dependency in `app/api/deps.py`. `User.role` now has a real consumer (`role="admin"` bypasses project visibility checks, see below) but there's still no route that *requires* admin — it's opt-in bypass only, not gating.
- **Projects & Folders**: full CRUD, layered as `router → service → repository → model`. `created_by` is filled server-side from the logged-in user. Folder moves are cycle-checked. **Access control (2026-08-20)**: see the dedicated bullet below — this used to be "auth-protected only, no per-project access control," which is no longer accurate.
- **프로젝트 멤버십 & 가시성 (2026-08-20, DESIGN.md §28)**: closes a real gap — until this, `get_current_user` only checked token validity, so any logged-in user could read/download/delete *any* project or document regardless of who made it (`list_projects`'s own docstring used to admit this). `projects` gained `owner_id` (FK `users.id`) + `visibility` (`private`/`invite`/`public`, default `public` — so nothing existing changed behavior on migration) and a new `project_members` table (`project_id, user_id, role[owner|member], invited_by`). Access is checked once per request via `app/api/deps.py`'s `require_project_access`/`require_project_owner`, or the sibling `check_document_access`/`check_version_access`/`check_folder_access` dependencies in `documents.py`/`folders.py`/`proofread.py` that resolve document/version/folder → project before checking — every document/folder/version/chunk/proofread endpoint is now gated, not just projects themselves. `public` keeps today's fully-open behavior (anyone authenticated can read *and* write, matching pre-existing behavior exactly); `invite`/`private` restrict to members/owner. Cross-project endpoints (`/documents/recent`, `/documents/search`, `/dashboard/summary`, `/activity`) now filter out documents/counts/logs from projects the caller can't access instead of leaking them. New: `PATCH /projects/{id}/visibility` (owner-only), `GET|POST /projects/{id}/members`, `DELETE /projects/{id}/members/{user_id}` (owner-only), `PATCH /documents/{id}/move` (moves a document to a different project the caller can also access — e.g. promoting a finished private draft into a shared project; physical `storage_path` is left as-is, only DB `project_id`/`folder_id` change). Existing rows backfilled: `visibility='public'` for all, `owner_id` parsed from `created_by` where numeric, and that owner registered in `project_members` for consistency with `create_project()`'s new behavior (every new project's creator becomes an `owner` member row too). No frontend wiring yet (invite UI, visibility toggle, move-document action).
- **Document Upload (Phase 5)**: multipart upload → validates extension/size → stores file via `StorageProvider` (local, under `storage/`) → creates `document` + `document_version` (v1, sha256) → `202`. Plus list/detail/versions/download/status/delete, all auth-protected. Detail & list are enriched with `author` (created_by id → name/email) and `current_version`.
- **Parse pipeline (Phase 6)**: a `BackgroundTasks` job (`run_parse_task`) parses the uploaded file into `document_sections` (hierarchy via parent_section_id + a `level` column — heading depth 1-9, body/table = 100; page/bbox in `meta` JSONB). **Section rule** (normalized in `parsing_service._persist_sections`, format-agnostic): `heading` sections carry `title` only (`content` emptied to avoid duplicate display); body/table carry `content` only. Format adapters in `app/services/parsing/`: TXT/MD, DOCX (python-docx, heading styles + tables), PDF (PyMuPDF native text + bbox + font-size heading heuristic, **+ Tesseract OCR fallback for scanned pages**, kor+eng), HWPX (OWPML XML), PPTX (python-pptx, slide→shape→paragraph, recursing into group shapes; title placeholder = heading, tables = table), XLSX (openpyxl, read-only — sheet name = heading, sheet data = one table section per sheet; no `apply` support yet, see backlog). `GET /versions/{id}/sections` exposes `level` so the frontend can render a collapsible tree.
- **OCR quality (scanned PDF pages)**: the OCR path (`app/services/parsing/ocr.py`, `pdf_parser.py`) now mirrors the native-text pipeline instead of dumping every line as flat body text. `preprocess_for_ocr()` runs grayscale → deskew (`minAreaRect` angle estimate, ±15° cap) → CLAHE contrast before Tesseract (no hard binarization — Tesseract's own LSTM Otsu step does better on grayscale input); needs `opencv-python-headless` (added to `requirements.txt`, no Dockerfile change since it's headless). Heading detection on OCR'd lines uses the same line-height-vs-median-ratio heuristic (×1.3) as the native path's font-size heuristic. Each OCR line below `OCR_LOW_CONFIDENCE_THRESHOLD` (60) gets `meta.low_confidence=true` (existing `document_sections.meta` JSONB, no migration) and the document-level ratio is logged as a warning at ≥30% low-confidence lines — server-log-only, no UI badge wired yet.
- **Chunking (Phase 7)**: same job continues into `document_chunks` — structure-aware (skips headings, carries a `heading_path` breadcrumb, sentence-split with overlap only when a section exceeds `chunk_max_chars`). `GET /versions/{id}/chunks`. Status flow: `UPLOADED→PARSING→PARSED→CHUNKING→CHUNKED` (terminal for now; `EMBEDDING→READY` comes with Phase 9).
- **Proofread (Phase 8, MVP1's last step) — now wired to real GPT, async + batch**: `POST /documents/{id}/proofread` validates + creates a `RUNNING` row and returns **`202` immediately**; a `BackgroundTasks` job (`run_proofread_task`) then runs the current version's parsed sections through an `LLMProvider` and updates the row to `COMPLETED`/`FAILED`. Frontend polls `GET /documents/{id}/analyses/{analysis_id}` (status RUNNING→COMPLETED). **Batching**: sections are grouped (`proofread_batch_max_chars`/`_max_sections`) and sent in one prompt via `[n]` markers → results remapped by index (11 sections: sequential ~17s → one batch ~7.5s, 11 calls → 1). Each finding: `original→suggestion`, `reason`, `category`, + `section_id`/page. **Scope is deliberately narrow** — `PROOFREAD_CATEGORIES` defaults to `["spelling","spacing"]` because on longer docs GPT floods the results with "make it flow better" expression/context notes and buries the actual typos (measured on one doc: 12 findings → 9, all 4 expression/grammar ones gone). The prompt narrows the target list, the forbidden list, **and the category enum together** — leaving the enum open just makes the model relabel excluded findings into whatever buckets remain. Anything that still leaks through is dropped by the provider and logged; unknown labels are coerced to the default category rather than dropped, so a mislabelled typo isn't lost. Add all four to `.env` to get expression fixes back. Results persist to a shared `ai_analysis_results` table (analysis_type=`proofread`; classify/validate/related reuse it). Provider abstraction in `app/services/llm/`: `MockLLMProvider` (rule-based, no key) + `OpenAILLMProvider` (httpx Chat Completions, `proofread`/`proofread_batch`); prompts live in `app/services/llm/prompts.py`. `LLM_PROVIDER=auto` auto-selects by `OPENAI_API_KEY` presence — **currently a real key is set, so proofread hits OpenAI GPT** (model via `OPENAI_MODEL`, e.g. `gpt-5.6-luna`; gpt-5.x models reject custom `temperature`, so it's omitted). `.env` change needs a **server restart** (env is read at startup; `--reload` only reloads code). See [[proofread-gpt-setup]].
- **Correction apply (new)**: findings now carry a stable `id` + accept/reject `status` (`PATCH /documents/{id}/analyses/{analysis_id}/findings/{finding_id}`, still just the same `result` JSONB, no migration). `POST /documents/{id}/analyses/{analysis_id}/apply` takes every `accepted` finding and writes a **new document version** — `app/services/correction_service.py` dispatches by extension: DOCX/HWPX/PPTX get a real text edit via `_replace_span_in_nodes` (a run/XML-text-node-boundary-aware substitution shared by all three formats — only the run(s)/`<hp:t>` node(s) the matched span actually touches get rewritten, so formatting outside the edited span survives; python-docx `Run`, python-pptx run, and `ElementTree` `Element` all just need `.text` get/set, so one function serves all three; table sections (all three formats) resolve to the one cell containing the match via `_apply_*_table_cell` before calling `_replace_span_in_nodes`, so a span is never searched for across cell boundaries), PDF gets a best-effort visual patch (bbox `add_redact_annot`+`apply_redactions` then `insert_textbox`, since PDF can't be losslessly edited), TXT/MD get a block-offset string splice. The new version re-runs the existing `run_parse_task` (parse+chunk), so corrected sections/chunks just fall out of the normal pipeline — no hand-patching DB content. One-shot per analysis: `result.applied_version_id` guards a second `apply` call (409). `DocumentService.create_version()` is the new v2+-from-bytes helper (`upload_document` still owns v1-with-a-new-Document). No frontend wiring yet (accept/reject UI, apply button).
- **Dashboard & activity log (2026-08-16, scoping updated 2026-08-20)**: `GET /dashboard/summary`, `GET /activity`, `GET /documents/recent` — stats/weekly-processing/pipeline-status aggregation + an append-only `activity_logs` table (12 action codes, no FKs — deletion doesn't cascade the log away, `actor_label`/`target_label` snapshot names so history survives deletes). Dashboard response schemas alias to camelCase (rest of the API stays snake_case) to match a frontend contract set in advance. See api-spec.md §2 for the `targetType`/`targetId`/`targetAlive` link-safety rule frontend must apply. `GET /rag/history` (also under this section in the spec) is still ⏳ — no RAG yet to have history of. **Scoping (2026-08-20)**: when `project_id` is omitted, non-admin callers now only see counts/logs from projects they can access (public + their invite/private ones) instead of the org-wide total — see the membership/visibility bullet above. `role="admin"` still sees everything, unscoped. (`/mypage` remains the separate `created_by`-filtered "my own stuff" view, unaffected by this.)
- **마이페이지 API (2026-08-20)**: `GET /mypage/summary` — the user-scoped counterpart to the dashboard's org-wide numbers. Returns `profile`(id/email/name/role/provider/lastLoginAt/memberSince, camelCase like dashboard) + `stats`(projects/documents/processing, filtered by `created_by == str(user.id)`) + `recentActivity`(reuses `ActivityItem`, filtered by `activity_logs.actor_id == user.id`). `app/services/dashboard_service.py`'s `DashboardRepository.count_projects/count_documents/pipeline_counts` and `ActivityLogRepository.list_recent` all gained an optional `created_by`/`actor_id` param for this (default `None` = unchanged existing behavior); `DashboardService.get_activity` gained an internal `actor_id` param too, but it's **not** exposed on the public `/activity` route's query params — only `MyPageService` calls it. `app/services/mypage_service.py`, `app/schemas/mypage.py`, `app/api/v1/mypage.py`.
- **문서 검색 (2026-08-20)**: `GET /documents/search?q=&limit=` — global, project-crossing keyword search over `documents.name`/`description` (`ILIKE`). Same response shape as `/documents/recent` (`RecentDocumentRead`), reused as-is. Wires up the Topbar's "문서 · 프로젝트 검색" input (`frontend/src/components/layout/Topbar.tsx`), which was a non-functional skeleton before this. **Detail/faceted search (project/status/date-range filters) isn't built yet** — this is name/description substring matching only; see [docs/ROADMAP.md](ROADMAP.md).
- **문서 비교 / Version Diff (2026-08-20, MVP4 backend done)**: `GET /documents/{doc_id}/diff?from_version_id=&to_version_id=` — compares two versions' `document_sections` and returns section-level `added`/`deleted`/`modified`/`unchanged` plus, for `modified` sections, a word-level token diff (`{op: equal|insert|delete, text}[]`) that a frontend can render like an IntelliJ/git diff view (concatenating tokens losslessly reconstructs the original text). **No embeddings, no LLM, no `ai_analysis_results` row** — this isn't a search problem (comparing many documents to find similar ones), it's comparing two already-known versions of the same document, so it's computed synchronously from data already in `document_sections` via stdlib `difflib` (section alignment via `SequenceMatcher.get_opcodes()` on `(level, section_type, normalized_text)` keys, with a similarity-ratio threshold inside `replace` blocks to avoid pairing unrelated sections). Nothing is persisted — recomputed on every request. `app/services/diff_service.py`, `app/schemas/diff.py`. No frontend wiring yet.
- **멤버 초대 UX 백엔드 3종 (2026-08-20)** — 프론트가 초대 화면을 만들려면 없어서 막혀 있던 세 가지를 채웠다. 세부 계약은 [docs/api-spec.md](api-spec.md) §3·§9.
  1. **사용자 검색**: `GET /users/search?q=&limit=&exclude_project_id=` (신규 `app/api/v1/users.py`, `app/services/user_service.py`, `UserRepository.search`). 이전에는 `/users` 라우터가 아예 없고 `get_by_email`(완전 일치)뿐이라 프론트가 "이메일을 정확히 타이핑"하는 UI밖에 만들 수 없었다. 이름/이메일 `ILIKE` 부분일치 + 앞부분 일치 우선 정렬, 최소 2자, 비활성 사용자 제외, 응답은 `id/email/name`만. `exclude_project_id`로 이미 초대·가입한 사람(`active`+`pending`)을 걸러 주되 그 필터는 해당 프로젝트 접근 권한이 있는 사람만 쓸 수 있다(멤버 목록 간접 유출 차단). 사용자 입력의 `%`/`_`/`\`는 이스케이프해 리터럴로 취급한다.
  2. **초대 대기(pending) 상태**: `project_members`에 `status`(`pending`/`active`/`rejected`, 기존 행은 `server_default='active'`로 동작 불변) + `responded_at` 추가(마이그레이션 `7ba371bea0ec`). `POST /projects/{id}/members`는 이제 **즉시 멤버를 만들지 않고** `pending` 초대장만 만들고, `user_id`(검색 결과에서 클릭) 또는 `email` 중 하나를 받는다. 초대받은 사람은 `GET /projects/invitations`(수락 전에는 접근 권한이 없어 `GET /projects`에 안 나오므로 별도 경로 — **`/{project_id}` 라우트보다 먼저 선언해야 한다**)로 확인하고 `POST /projects/{id}/invitation/accept`(→`active`, 이때부터 접근 가능) 또는 `.../decline`(→`rejected`, 행이 남아 owner가 "거절함"을 보고 재초대하면 같은 행이 다시 `pending`)을 호출한다. **접근 제어는 이제 `status='active'`만 통과** — `ProjectService._can_access`는 `members.get_active()`를, `ProjectRepository._accessible_condition`은 `status == 'active'` 조건을 쓴다(두 곳이 같은 규칙이어야 하는 기존 제약 그대로). `DELETE .../members/{user_id}`가 "수락 전 초대 취소"를 겸하고, 지워진 행의 `status`를 서비스가 돌려줘 라우터가 초대 취소(알림 없음)와 정식 멤버 제거(알림 발송)를 구분한다. 활동 코드 2개 추가(`project.member_accept`/`project.member_decline`).
  3. **알림**: 신규 `notifications` 테이블 + `GET /notifications`(목록+전체 미읽음 수), `GET /notifications/unread-count`, `POST /notifications/{id}/read`, `POST /notifications/read-all`. `activity_logs`에 읽음 레이어를 얹는 대신 **수신자별 테이블을 따로** 뒀다 — 조회 축이 "프로젝트에서 무슨 일이 있었나"(감사)와 "이 사용자가 봐야 할 것"(수신자+읽음)으로 다르고, 활동 한 건의 수신자가 0명일 수도 여러 명일 수도 있다. `app/services/notification_service.py`의 `notify()`가 **인앱 행 저장 + Web Push 발송을 한 번에** 처리하고, `ActivityService.record()`와 같은 원칙으로 실패해도 본 업무(초대/분석)를 깨뜨리지 않는다. 초대/수락/거절/멤버제거가 이 경로로 알림을 보내며, 기존 오탈자 검증 완료·실패 push도 이 서비스를 거치게 바꿔 **이제 알림함에 기록이 남는다**(이전엔 push만 쏘고 흔적 없음). 남의 알림 id로 읽음 처리하면 404(존재 은닉). Web Push payload는 서비스워커 계약으로 `{title, body, url, type}` 4키 고정 — `type`을 추가해 SW가 `showNotification`의 `tag`/아이콘을 종류별로 분기할 수 있게 했다. 서버 푸시→클라이언트 알림 전달은 **폴링 기반**(SSE/WebSocket 없음)이라 벨 뱃지는 `/notifications/unread-count`를 주기 조회해야 한다.
  - 스모크 테스트(임시 스크립트, TestClient + 실제 DB, 39개 체크 전부 통과 후 삭제)로 검증: 검색·제외 필터·403, 초대→pending, 중복 초대 400, 수락 전 403/목록 미노출, 초대 목록·알림 도착, 거절→rejected→재초대→수락→접근 가능, 제거 후 403 + 알림, 읽음/전체읽음/타인 알림 404, owner 자기 제거 403. **정식 테스트 러너(pytest)는 여전히 없다.**
  - **아직 없음**: 프론트 UI 전부(초대 화면·초대함·알림 벨), 이메일 알림, 알림 삭제/보관 엔드포인트, 미가입자 초대(가입된 사용자만 초대 가능 — 이메일 초대장 발송은 미도입).
- **health**: `/api/v1/health` pings the DB.
- **Not yet**: embedding / RAG (Phase 9); a general user-facing "upload a new version of this doc" endpoint — v2+ creation as a *mechanism* now exists (`DocumentService.create_version`) but is only reachable today via the proofread-apply flow above, not its own upload route; SSE; a parser for hwp (uploads but `FAILED` on parse; pptx and xlsx now have parsers, see backlog below); `apply`(교정 적용) for XLSX (parse/조회만 지원, 표 셀 교정 반영은 아직); real `created_by` FK (still a string column, parsed on the fly — `owner_id` on `projects` *is* now a real FK, added 2026-08-20, but `documents.created_by`/`projects.created_by` themselves are not). `members`(membership table) and document `PATCH .../move` **shipped 2026-08-20** — see the membership/visibility bullet above (there's no generic `PATCH /documents/{id}` for rename/retype yet, only the move-project endpoint). Frontend wiring for the async proofread poll + section tree render + accept/reject/apply UI, and for the new visibility/invite/move UI, is still pending.
