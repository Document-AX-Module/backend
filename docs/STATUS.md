# 구현 현황 (Implementation Status)

`CLAUDE.md`에서 분리된 문서입니다. 기능이 실제로 백엔드에 구현되어 있는지 아닌지를 기능 단위로, 날짜와 함께 기록합니다. **새 기능을 완성했으면 이 문서를 갱신하세요** — CLAUDE.md에는 짧은 요약과 이 문서로의 링크만 남깁니다.

이 저장소는 **AX Document Platform**의 **backend**입니다 — 프로젝트 단위 문서를 공유 **Document Core**(File → Version → Section → Chunk → Embedding)로 통합 관리하고, 그 위에 proofread(오탈자 검증), 자동분류, 버전 diff, 규정검증, RAG 챗봇, 관련문서 추천 등 AI 기능을 얹는 프로젝트-스코프 문서 플랫폼입니다. 상위 모노레포 스타일 디렉터리(`sidepjt/`) 아래, 형제 폴더 `frontend/`(Next.js, 별도 git 저장소), `embedding/`, `storage/`, `models/`, `docker/`와 함께 있으며, 루트 `docker-compose.yml`이 부모 디렉터리에서 전체를 오케스트레이션합니다.

## What actually exists today (don't overstate)

- **DB / migrations**: the full Document Core schema (8 tables: projects, folders, documents, document_versions, document_sections, document_chunks, embedding_models, chunk_embeddings) + a `users` table, all created via **Alembic** migrations. `chunk_embeddings.embedding` is `pgvector.Vector(1024)`.
- **Auth**: Google OAuth + backend-issued JWT (access via `Authorization: Bearer`, refresh in httpOnly cookie), plus a `mock` provider for dev login without credentials. `get_current_user` dependency in `app/api/deps.py`. `User.role` now has a real consumer (`role="admin"` bypasses project visibility checks, see below) but there's still no route that *requires* admin — it's opt-in bypass only, not gating.
- **Projects & Folders**: full CRUD, layered as `router → service → repository → model`. `created_by` is filled server-side from the logged-in user. Folder moves are cycle-checked. **Access control (2026-08-20)**: see the dedicated bullet below — this used to be "auth-protected only, no per-project access control," which is no longer accurate.
- **프로젝트 멤버십 & 가시성 (2026-08-20, DESIGN.md §28)**: closes a real gap — until this, `get_current_user` only checked token validity, so any logged-in user could read/download/delete *any* project or document regardless of who made it (`list_projects`'s own docstring used to admit this). `projects` gained `owner_id` (FK `users.id`) + `visibility` (`private`/`invite`/`public`, default `public` — so nothing existing changed behavior on migration) and a new `project_members` table (`project_id, user_id, role[owner|member], invited_by`). Access is checked once per request via `app/api/deps.py`'s `require_project_access`/`require_project_owner`, or the sibling `check_document_access`/`check_version_access`/`check_folder_access` dependencies in `documents.py`/`folders.py`/`proofread.py` that resolve document/version/folder → project before checking — every document/folder/version/chunk/proofread endpoint is now gated, not just projects themselves. `public` keeps today's fully-open behavior (anyone authenticated can read *and* write, matching pre-existing behavior exactly); `invite`/`private` restrict to members/owner. Cross-project endpoints (`/documents/recent`, `/documents/search`, `/dashboard/summary`, `/activity`) now filter out documents/counts/logs from projects the caller can't access instead of leaking them. New: `PATCH /projects/{id}/visibility` (owner-only), `GET|POST /projects/{id}/members`, `DELETE /projects/{id}/members/{user_id}` (owner-only), `PATCH /documents/{id}/move` (moves a document to a different project the caller can also access — e.g. promoting a finished private draft into a shared project; physical `storage_path` is left as-is, only DB `project_id`/`folder_id` change). Existing rows backfilled: `visibility='public'` for all, `owner_id` parsed from `created_by` where numeric, and that owner registered in `project_members` for consistency with `create_project()`'s new behavior (every new project's creator becomes an `owner` member row too). No frontend wiring yet (invite UI, visibility toggle, move-document action).
- **Document Upload (Phase 5)**: multipart upload → validates extension/size → stores file via `StorageProvider` (local, under `storage/`) → creates `document` + `document_version` (v1, sha256) → `202`. Plus list/detail/versions/download/status/delete, all auth-protected. Detail & list are enriched with `author` (created_by id → name/email) and `current_version`.
- **Parse pipeline (Phase 6)**: a `BackgroundTasks` job (`run_parse_task`) parses the uploaded file into `document_sections` (hierarchy via parent_section_id + a `level` column — heading depth 1-9, body/table = 100; page/bbox in `meta` JSONB). **Section rule** (normalized in `parsing_service._persist_sections`, format-agnostic): `heading` sections carry `title` only (`content` emptied to avoid duplicate display); body/table carry `content` only. Format adapters in `app/services/parsing/`: TXT/MD, DOCX (python-docx, heading styles + tables), PDF (PyMuPDF native text + bbox + font-size heading heuristic, **+ Tesseract OCR fallback for scanned pages**, kor+eng), HWPX (OWPML XML), PPTX (python-pptx, slide→shape→paragraph, recursing into group shapes; title placeholder = heading, tables = table), XLSX (openpyxl, read-only — sheet name = heading, sheet data = one table section per sheet; no `apply` support yet, see backlog). `GET /versions/{id}/sections` exposes `level` so the frontend can render a collapsible tree.
- **OCR quality (scanned PDF pages)**: the OCR path (`app/services/parsing/ocr.py`, `pdf_parser.py`) now mirrors the native-text pipeline instead of dumping every line as flat body text. `preprocess_for_ocr()` runs grayscale → deskew (`minAreaRect` angle estimate, ±15° cap) → CLAHE contrast before Tesseract (no hard binarization — Tesseract's own LSTM Otsu step does better on grayscale input); needs `opencv-python-headless` (added to `requirements.txt`, no Dockerfile change since it's headless). Heading detection on OCR'd lines uses the same line-height-vs-median-ratio heuristic (×1.3) as the native path's font-size heuristic. Each OCR line below `OCR_LOW_CONFIDENCE_THRESHOLD` (60) gets `meta.low_confidence=true` (existing `document_sections.meta` JSONB, no migration) and the document-level ratio is logged as a warning at ≥30% low-confidence lines — server-log-only, no UI badge wired yet.
- **Chunking (Phase 7, extended 2026-08-25 — structure/semantic auto-split)**: same job continues into `document_chunks`. `app/services/chunking_service.py` is now orchestration-only — it auto-detects per version whether any `document_sections` row has `section_type=="heading"`, and picks **structure-aware** chunking (`app/services/chunking/structure_chunker.py`, unchanged logic: skips headings, carries a `heading_path` breadcrumb, sentence-split with overlap only past `chunk_max_chars`) for structured docs (회사 내규 등), or **semantic** chunking (`app/services/chunking/semantic_chunker.py`, new) for flat/unstructured docs (txt/hwpx, docx without styles) that never got a heading in the first place. Semantic chunking embeds sliding sentence-windows (`chunk_semantic_sentence_window`, default 3) via the active `EmbeddingProvider` and cuts a boundary where the inter-window cosine distance exceeds a percentile threshold (`chunk_semantic_breakpoint_percentile`, default 95 — LlamaIndex `SemanticSplitterNodeParser` method), then still runs the merged text through the same `split_to_size` safety net (max-chars/overlap/hard-wrap). Every chunk's `chunk_metadata.chunking_strategy` records which path produced it. `GET /versions/{id}/chunks`. Status flow: `UPLOADED→PARSING→PARSED→CHUNKING→CHUNKED→EMBEDDING→READY` (see Phase 9 bullet — if there's no active embedding model, or the embedding step itself fails for any reason, the version reverts to/stays `CHUNKED` rather than `FAILED`, since proofread etc. only need `CHUNKED`).
- **Local embedding pipeline + EmbeddingLab backend (Phase 9, 2026-08-25 — infra only, not yet exercised end-to-end)**: `app/services/embedding/` mirrors the `llm/` provider pattern — `EmbeddingProvider` Protocol (`load/embed_documents/embed_query/get_dimension/get_model_name`, matches DESIGN.md §12) implemented by `SentenceTransformerProvider` (loads `sentence-transformers` in-process, lazily on first use, cache dir `EMBEDDING_CACHE_DIR`), behind a process-wide LRU cache (`get_embedding_provider`, `EMBEDDING_MAX_LOADED_MODELS`) so repeated calls/benchmark runs don't reload a model per call. `app/main.py` startup seeds `embedding_models` from `EMBEDDING_MODEL_KEY`/`EMBEDDING_MODEL_NAME` (default `kure-v1` / `nlpai-lab/KURE-v1`, 1024-dim) if the row doesn't exist yet, activating it if nothing else is active. `run_parse_task` now chains parse→chunk→**embed** (`embed_version` in `app/services/embedding_service.py`): batches `document_chunks` through the active model's `embed_documents`, writes `chunk_embeddings` (skipping chunk_ids that already have a row for that model — retry-safe), `CHUNKED→EMBEDDING→READY`. **If there's no active model, or the embed step throws for any reason (missing `sentence-transformers`/`torch`, no network to download the model, OOM, ...), the version reverts to `CHUNKED` and logs — it never becomes `FAILED` from an embedding problem**, so proofread and everything else gated on `_READY_STATES` keeps working. New admin-only (`require_admin`, new dep in `app/api/deps.py` — first real consumer of `User.role=="admin"` as a hard gate, not just a bypass) router `app/api/v1/embedding.py` (`/api/v1/embedding/...`, tag `embedding-lab`): `GET/POST /models`, `POST /models/{id}/activate`, `POST /models/{id}/reembed` (re-embeds all `document_chunks` with a different model, chunking untouched); `GET/POST /datasets`, `GET /benchmarks`, `POST /benchmarks/run`, `GET /benchmarks/{id}`, `POST /benchmarks/{id}/apply`; `POST /migrate`, `GET /jobs/{id}`. **Benchmarking is ephemeral by design** — `app/services/benchmark/runner.py` chunks+embeds the dataset's target documents in-memory per (model × chunking-config) combo and scores Recall@1/3/5/MRR/NDCG/latency/throughput/RAM (`app/services/benchmark/scoring.py`, DESIGN.md §9 weights) against `benchmark_questions.ground_truth` (a `{document_id, expected_snippet}` list, not a `section_id` FK — sections get replaced wholesale on every re-parse, so an FK would break on the next reparse); nothing touches the live `document_chunks`/`chunk_embeddings` tables. `apply` promotes a validated (chunking-config, model) pair into new `chunking_configs`/`embedding_models` active rows but **does not** touch existing documents — that's what `/migrate` is for (admin picks specific `document_version_id`s, e.g. old flat/unstructured docs, to re-chunk+re-embed in place; no new `document_version` is created since the source file didn't change). New tables (migration `a2ff50d158bd`): `chunking_configs` (the "active chunking params" analogue of `embedding_models.is_active`, deliberately a separate table so switching the active model doesn't also silently change chunking params), `embedding_jobs` (reembed/migrate progress polling), `benchmark_datasets`/`benchmark_questions`/`benchmark_runs`/`benchmark_results`. **What's verified**: migration applied cleanly; server boots and seeds the model row; a structured `.md` upload runs the real parse→chunk pipeline end-to-end and lands on `CHUNKED` with `chunking_strategy:"structure"` chunks; the semantic-chunker's boundary-detection math was unit-tested against a fake provider (topic-shift correctly becomes a chunk boundary); the benchmark run/apply/error-isolation-per-model flow was smoke-tested via the API. **실전 검증됨 (2026-08-25, 위 "not verified" 서술을 대체)**: `torch`/`sentence-transformers`가 host `.venv`에 설치되고 `KURE-v1`이 `EMBEDDING_CACHE_DIR`(`../models`, 2.27GB)에 완전히 내려와 있다 — CPU 로드 10.1초, dim=1024, 벡터는 정규화되어 있어(`normalize_embeddings=True`) **L2 norm=1.0 → 코사인 = 내적**. 운영 DB 상태: `embedding_models`에 `kure-v1` ACTIVE, `document_versions` READY 14 / CHUNKED 19, `chunk_embeddings` 445행, 실제 `chunking_strategy:"semantic"` 청크 109개(중간값 818자) 존재. pgvector 검색도 스모크됨(`1 - (embedding <=> :q)`, 435청크 대상 5~46ms, "개인정보 파기 규정" → 실제 개인정보 파기 항목 0.62로 1~2위) — 이 SQL은 이제 `app/repositories/rag_repository.py`의 실제 서비스 코드다(위 RAG 챗봇 항목). **남은 구멍**: CHUNKED 19버전(1465청크)은 임베딩이 없어 **검색에서 조용히 빠진다**(`/embedding/migrate`로 소급 필요), 벡터 인덱스(HNSW/ivfflat)는 아직 없음(현재 규모에선 seq scan으로 충분) — FTS(tsvector+GIN)는 이후 하이브리드 검색 작업(아래 RAG 챗봇 섹션 하단)으로 추가됨. `POST /api/v1/rag/query` itself (the actual chat endpoint, api-spec.md §6) is still ⏳ — this phase only built the retrieval *substrate* (chunks with real vectors in `chunk_embeddings`), not a query/answer endpoint. - **하이브리드 검색 (2026-08-25) — 벡터 + PostgreSQL FTS, RRF 융합**: `document_chunks`에 생성 컬럼 `content_tsv tsvector GENERATED ALWAYS AS (to_tsvector('simple', content)) STORED` + GIN 인덱스(마이그레이션 `c1a2b3d4e5f6`). `Retriever.retrieve()`가 이제 벡터 후보(`search()`)와 전문 후보(`ChunkSearchRepository.search_fts()`)를 각각 `RAG_HYBRID_CANDIDATE_K`(기본 20)개씩 뽑아 **Reciprocal Rank Fusion**(`score = Σ 1/(RAG_HYBRID_RRF_K + rank)`, 기본 k=60, Elasticsearch 기본값)으로 합친 뒤 최종 top_k를 자른다 — 두 점수는 스케일이 전혀 달라(코사인 0~1 대 `ts_rank_cd` 임의 실수) 값을 직접 더칠 수 없어 등수만 쓴다. `RAG_HYBRID_ENABLED=false`로 벡터 단독 모드로 롤백 가능.

AND가 아니라 OR인 이유: 자연어 질문(조사·의문사 섞인 긴 문장)을 전부 AND로 요구하면 대부분 0건이 되고, 여러 토큰이 맞을수록 `ts_rank_cd`가 자연히 더 높은 순위를 준다.
